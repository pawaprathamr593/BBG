# Display BBG Contribution Number (BCN) on approved subscriptions

## 1. Problem

An approved business subscription needs a permanent, human-readable BBG Contribution Number (BCN). Admins and business owners need to see the same identifier so they can reference the approved subscription in support, payment and operational conversations.

The BCN is generated by the backend when the Platform Admin approves the subscription. The Angular application must display the value returned by the backend and must not generate or modify it.

## 2. Personas

| Persona | Device | Goal |
| --- | --- | --- |
| Platform Admin | Desktop / tablet | Identify an approved subscription and communicate its BCN |
| Business Owner / Tenant Admin | Desktop / tablet / mobile | View and copy the BCN associated with the approved subscription |

## 3. Scope

**In scope:**
- Display the BCN for an approved subscription in the existing Platform Admin subscription detail/list experience where subscription identifiers are shown. The existing Plan reviews screen now includes both pending and active subscriptions so an Admin can reopen an approved subscription and view its BCN.
- Display the same BCN in the business owner's subscription history/list.
- Present the BCN as read-only text with a copy action where the existing UI patterns support it.
- Keep expiry information visible alongside the BCN so the YYMM portion can be understood.
- Handle loading, missing-value, error and success states without presenting an unconfirmed BCN.

**Out of scope:**
- Generating, formatting, sequencing or validating BCNs in Angular.
- Allowing admins or business owners to enter, edit or delete a BCN.
- Changing subscription approval, payment, renewal, expiry or plan-pricing business rules.
- Defining or changing backend API routes or payloads in this frontend requirement.
- Changing unrelated subscription screens or permissions.

## 4. Entry and context

- Routes: existing `/dashboard/subscription-approval` and `/dashboard/subscriptions` workspace sections. The implementation reuses their current API routes; no new route was added.
- Required params / auth / workspace context:
  - Platform Admin must have the existing permission required to view subscription review/details.
  - Business Owner must be authenticated and scoped to their own tenant.
  - BCN visibility is controlled by backend authorization and returned subscription data; hiding a UI element is not an authorization control.

## 5. Flow

### Platform Admin
1. Open the existing subscription review queue.
2. Open a subscription and review its details.
3. Before approval, no BCN is displayed.
4. Approve the subscription using the existing approval action.
5. After the backend confirms successful approval, refresh or consume the returned subscription data.
6. Display the generated BCN as read-only information.
7. Allow copying the BCN using the established copy interaction.
8. If approval fails, show the existing error feedback and do not display a newly generated or speculative BCN.

### Business Owner
1. Open the existing subscription area.
2. Open an approved subscription from the subscription list/history.
3. Display the same BCN stored for that subscription, together with its plan and expiry details.
4. Allow copying the BCN using the established copy interaction.
5. Pending or rejected subscriptions must not show a BCN.
6. If the subscription data cannot be loaded, show the existing error/retry state and do not fabricate a BCN.

## 6. Screens / regions

| Region | Intent | Reuse expectation |
| --- | --- | --- |
| Admin subscription detail | Show BCN after approval | Reuse existing subscription detail layout and typography |
| Admin subscription list/review result | Make BCN discoverable after approval if the list already exposes subscription identifiers | Reuse existing table/list column patterns; do not force a new column if it harms responsive layout |
| Business-owner subscription detail/history | Show the same BCN for an approved subscription | Reuse existing subscription detail/history components |
| BCN value | Read-only identifier and copy affordance | Use the browser Clipboard API with existing BBG notice/error feedback |

## 7. API

| Operation | Method | Path | Envelope / action | BCN location |
| --- | --- | --- | --- | --- |
| Admin subscription approval | POST | `/api/v1/admin/subscriptions/approve` | `adminParam` / `approveSubscription` | `data.bcn` |
| Admin active subscriptions | POST | `/api/v1/admin/subscriptions/active/list` | `adminParam` / `listActiveSubscriptions` | `data.items[].bcn` |
| Admin subscription detail | POST | `/api/v1/admin/subscriptions/detail` | `adminParam` / `getSubscriptionForReview` | `data.subscription.bcn` |
| Business-owner subscriptions | POST | `/api/v1/subscriptions/mine/list` | `subscriptionParam` / `listMySubscriptions` | `data.items[].bcn` |

The implementation extends these existing operations only. No new route, action type, envelope or permission was introduced.

## 8. Permissions

| Action | Permission key | Status |
| --- | --- | --- |
| View admin subscription details and approval result | Existing subscription-review permission | Reuse existing key; verify exact key in implementation |
| View own tenant subscription details | Existing tenant subscription permission | Reuse existing key; verify exact key in implementation |
| Copy visible BCN | No additional permission | Client-side action on data already authorized by backend |

Do not introduce new permission keys for BCN display.

## 9. Rules and validation

- Display a BCN only when the subscription is in the approved/active state and the backend supplies a non-empty BCN.
- Pending and rejected subscriptions must not display a BCN.
- The frontend treats BCN as opaque display data. It must not parse, reformat, recalculate or derive its segments.
- Display exactly the backend-provided value, preserving uppercase letters, digits and hyphens.
- BCN is read-only; no edit, delete or manual generation controls.
- The same stored BCN must be shown to the Platform Admin and the owning tenant.
- The expected format is **BCN-YYMMPID-SN**.
- Example: `BCN-271203-00125` (illustrative: `BCN` prefix, expiry month `2712`, plan ID `03`, serial `00125`).
- Plan-ID and serial-number padding are backend-owned. The frontend displays and copies the returned value without changing it.

## 10. UI states

- **Loading:** use the existing subscription loading state.
- **Empty / not applicable:** do not render a BCN for pending or rejected subscriptions. Do not show a placeholder that looks like an identifier.
- **Error:** use existing error and retry behaviour; never synthesize a BCN.
- **Success:** display the exact BCN returned by the backend for the approved subscription. Admin approval feedback includes the generated BCN; active Admin and tenant records show the read-only BCN with a copy action.
- **Permission denied:** preserve existing authorization handling; do not expose subscription data through an alternate UI path.
- **Copy success/failure:** provide feedback consistent with the existing copy interaction.

## 11. Responsive and theme

- BCN must remain readable on mobile without causing horizontal overflow.
- Allow wrapping or use a compact identifier presentation while preserving the exact copied value.
- Keep copy affordance reachable by keyboard and touch.
- Follow existing light/dark theme tokens and accessible contrast.
- Do not introduce a new component library or design system.

## 12. Acceptance criteria

1. Given a subscription is pending, when an Admin or Business Owner views it, then no BCN is displayed.
2. Given a subscription is rejected, when an Admin or Business Owner views it, then no BCN is displayed.
3. Given the Admin approves a subscription and the backend confirms success with a BCN, when the approval result is rendered, then the exact returned BCN is displayed.
4. Given a subscription is approved, when its owning Business Owner opens its details, then the same BCN stored by the backend is displayed.
5. Given a BCN is displayed, when the user copies it, then the clipboard receives the exact value without formatting changes.
6. Given approval fails, when the UI renders the result, then it does not display a newly generated or guessed BCN.
7. Given a BCN is displayed on a narrow viewport or in dark mode, when the page is rendered, then the identifier remains readable and the layout remains usable.
8. Given the backend returns no BCN for a subscription, when the UI renders it, then the UI does not generate one locally.

## Implementation decisions

- The backend response property is `bcn` on the approval result, admin subscription detail/active-list records, and tenant subscription-list records.
- The existing Admin Plan reviews screen loads both pending and active subscriptions using existing Admin APIs; no new route or permission was added.
- The existing tenant Subscriptions & plans screen displays BCN for active/expired approved records.
- BCN is treated as opaque text. The UI uses the browser clipboard API and does not parse or format the identifier.
- The backend applies minimum widths of two digits for plan ID and five digits for serial; values are not truncated when wider.
- Each newly approved subscription record, including a renewal request that creates a new record, receives its own BCN. Existing records retain their original BCN.
- Existing approved subscriptions predating the migration are not backfilled.
